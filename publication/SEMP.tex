\subsection{1. Purpose and Scope}\label{purpose-and-scope}

The \textbf{System Engineering Management Plan (SEMP)} defines how
systems engineering will be planned, organized, conducted, and
controlled for the \textbf{SysML Cloud Platform} project. This plan
ensures that all systems engineering activities align with project
objectives and organizational standards.

\subsubsection{1.1 Project Vision}\label{project-vision}

Transform system models into actionable implementation artifacts through
a Git-native, model-driven engineering framework that connects SysML v2
system architecture with cloud infrastructure, technicians, and
developers.

\subsubsection{1.2 Scope}\label{scope}

\begin{itemize}
\tightlist
\item
  Model-driven design of datacenter and cloud infrastructure
\item
  Integration of SysML requirements, architecture, and deployment models
\item
  Automated generation of documentation, diagrams, and deployment
  artifacts
\item
  Bidirectional traceability from requirements through implementation
  and operations
\end{itemize}

\subsection{3. Systems Engineering
Processes}\label{systems-engineering-processes}

\subsubsection{3.1 Integrated SE Process
Model}\label{integrated-se-process-model}

The project follows a \textbf{model-driven, iterative SE cycle}:

\begin{verbatim}
Requirements → Architecture → Design → Implementation → Validation → Operations
     ↑                                                                    ↓
     └────────────────────── Feedback & Refinement ──────────────────────
\end{verbatim}

\subsubsection{3.2 Requirements
Management}\label{requirements-management}

\textbf{Definition:} Capture stakeholder needs and system requirements
in SysML requirement blocks.

\textbf{Key Activities:} - Elicit requirements from stakeholders
(operators, developers, security, compliance) - Document requirements in
SysML format under \texttt{sysml/*/} - Establish requirement IDs and
traceability links - Manage requirement changes through Git commits with
clear commit messages

\textbf{Artifacts:} -
\texttt{sysml/datacenter/DatacenterRequirements.sysml} -
\texttt{sysml/infrastructure/InfrastructureRequirements.sysml} -
\texttt{sysml/overall-design/SysMLCloudPlatformRequirements.sysml}

\textbf{Tools:} SysML text/graphical editors, Git version control

\subsubsection{3.3 Architecture and
Design}\label{architecture-and-design}

\textbf{Definition:} Develop high-level system architecture using SysML
block definition diagrams (BDD) and internal block diagrams (IBD).

\textbf{Key Activities:} - Define major system blocks (components,
subsystems) - Specify interfaces and connections - Decompose
requirements into design elements - Document deployment views and
physical architecture

\textbf{Artifacts:} -
\texttt{sysml/datacenter/DatacenterArchitectureModel.sysml} -
\texttt{sysml/infrastructure/ClusterArchitectureModel.sysml} -
\texttt{sysml/overall-design/SysMLCloudPlatformModel.sysml} -
\texttt{fabrications/*/} --- Specific datacenter/rack designs -
\texttt{configs/*/} --- Cluster and infrastructure specifications

\textbf{Tools:} SysML modelers, Graphviz for diagram rendering

\subsubsection{3.4 Implementation}\label{implementation}

\textbf{Definition:} Transform SysML models into executable code,
infrastructure definitions, and deployment configurations.

\textbf{Key Activities:} - Generate Terraform modules and Ansible
playbooks from SysML deployment views - Create Python/scripting stubs
for system components - Define network models, service catalogs, and
virtualization configs - Commit implementation artifacts to Git with
full traceability

\textbf{Artifacts:} - \texttt{library/terraform-modules/} --- IaC
templates - \texttt{library/ansible-roles/} --- Deployment automation -
Generated scripts and configuration files - Infrastructure-as-Code (IaC)
documentation

\textbf{Tools:} Terraform, Ansible, Python, \texttt{build-docs.py}
script

\subsubsection{3.5 Verification and
Validation}\label{verification-and-validation}

\textbf{Definition:} Ensure SysML models, requirements, and
implementations are correct and complete.

\textbf{Verification Activities:} - Review SysML models for completeness
and consistency - Validate model syntax with
\texttt{scripts/check-encoding.py} - Trace requirements to design
elements - Peer review of architecture and design documents

\textbf{Validation Activities:} - Deploy infrastructure using generated
Terraform/Ansible - Test system against original requirements - Collect
feedback from operators and stakeholders - Validate deployment in
staging/production environments

\textbf{Artifacts:} - Test plans and reports - Validation matrices
(requirement ↔ test case) - Deployment logs and metrics

\textbf{Tools:} Git, SysML tooling, deployment platforms (AWS, Azure,
etc.), monitoring tools

\subsubsection{3.6 Operations and
Maintenance}\label{operations-and-maintenance}

\textbf{Definition:} Manage the operational system and apply
updates/improvements.

\textbf{Key Activities:} - Monitor deployed systems; collect operational
metrics - Document design decisions and operational procedures - Process
change requests and improvements - Update SysML models to reflect
operational feedback

\textbf{Artifacts:} - Operational procedures and runbooks -
Incident/change logs - Updated SysML models and deployment
configurations

\textbf{Tools:} Monitoring solutions (Prometheus, OpenTelemetry), Git,
SysML tooling

\subsection{4. Traceability}\label{traceability}

\subsubsection{4.1 Traceability Links}\label{traceability-links}

All SE artifacts maintain bidirectional traceability:

\begin{verbatim}
Stakeholder Need
    ↓
SysML Requirement (e.g., REQ-001)
    ↓
SysML Design Element (e.g., Block, Interface)
    ↓
Implementation (Terraform, Ansible, Code)
    ↓
Deployment & Operations
    ↓
Feedback (Operational Metrics, Issues)
\end{verbatim}

\subsubsection{4.2 Traceability
Management}\label{traceability-management}

\begin{itemize}
\tightlist
\item
  \textbf{Requirements}: Stored as SysML \texttt{requirement} blocks
  with \texttt{Text}, \texttt{Id}, and relationship attributes
\item
  \textbf{Design ↔ Requirements}: SysML \texttt{refines},
  \texttt{derives}, \texttt{satisfies} relationships
\item
  \textbf{Implementation ↔ Design}: Code comments and configuration
  metadata reference SysML elements
\item
  \textbf{Validation ↔ Requirements}: Test cases linked to requirements
  via Git tags and documentation
\item
  \textbf{Tool Support}: Git blame/history, SysML tooling queries,
  custom traceability dashboards
\end{itemize}

\textbf{Repository Structure:}

\begin{verbatim}
sysml/
├── overall-design/          # Platform-wide models

├── infrastructure/          # Infrastructure domain
fabrications/
├── fabrication-datacenter-a/
configs/
├── infrastructure-cluster-a/
library/
├── terraform-modules/
├── ansible-roles/
publication/                 # Generated traceability reports
\end{verbatim}

\subsection{11.3 Documentation \& Publication
Structure}\label{documentation-publication-structure}

The project organizes documentation into a three-tier publication
structure that aligns with systems engineering disciplines and
traceability expectations.

\begin{itemize}
\item
  \textbf{System Design (system-level):} a PDF assembled from
  \texttt{overall-design} domain pages. This document describes the
  high-level architecture that connects all subsystems and provides the
  principal system-level decisions and interfaces. It is published as
  \texttt{publication/system-design.pdf}.
\item
  \textbf{Sub-System Design (subsystem-level):} separate PDF
  publications for each major subsystem. In this project the primary
  subsystems are:

  \begin{itemize}
  \tightlist
  \item
    \textbf{Fabrication Subsystem} (datacenter domain) --- published as
    \texttt{publication/fabrication-design.pdf} and assembled from
    \texttt{datacenter} domain pages (e.g.,
    \texttt{sysml/datacenter/*}).
  \item
    \textbf{Infrastructure Subsystem} (infrastructure domain) ---
    published as \texttt{publication/infrastructure-design.pdf} and
    assembled from \texttt{infrastructure} domain pages (e.g.,
    \texttt{sysml/infrastructure/*}).
  \end{itemize}

  Sub-System Design documents contain the architectural and design rules
  for their domain and are referenced by technical publications for
  specific deployments.
\item
  \textbf{Technical Publications (deployment-level):} per-site or
  per-cluster technical publications (for example
  \texttt{fabrications/fabrication-datacenter-a},
  \texttt{fabrications/fabrication-datacenter-b},
  \texttt{configs/infrastructure-cluster-a},
  \texttt{configs/infrastructure-cluster-b}). Each technical
  publication:

  \begin{itemize}
  \tightlist
  \item
    Is generated as a distinct PDF (e.g.,
    \texttt{publication/fabrications-fabrication-datacenter-a.pdf}).
  \item
    References its parent Sub-System Design document (e.g., Fabrication
    Subsystem) and the System Design where applicable.
  \item
    Contains detailed rack/datacenter or cluster-level models,
    configuration specs, and deployment instructions.
  \end{itemize}
\end{itemize}

This organization ensures a clean separation of concerns: - System
Design connects the dots and defines global interfaces and constraints.
- Sub-System Designs capture domain-specific architecture, constraints,
and design patterns. - Technical Publications provide concrete,
deployable specifications and instructions tied back to the above
designs with full traceability to requirements.

When generating publications via the repository automation
(\texttt{make\ docs} and \texttt{make\ pdf}), the pipeline produces one
PDF per publication type as described above and writes a
\texttt{manifest.json} to \texttt{publication/} containing the mapping
from generated markdown pages to their publication group. This manifest
supports downstream processing such as assembling PDFs and generating
cross-reference tables.
